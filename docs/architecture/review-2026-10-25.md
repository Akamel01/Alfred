## 1. Deepening opportunities (best first)

### 1.1 `src/provenance` — versioned stamping split across six modules
- Files: `src/provenance/stamp.py:1-200`, `src/provenance/stamp_v1.py`, `src/provenance/stamp_types.py`,
  `src/provenance/verify.py`, `src/provenance/encoding.py`, `src/provenance/upstream.py`, `src/provenance/__init__.py`.
- Problem: the stamp seam is deep in intent but shallow in navigation — a reader must open six files to
  learn that `ResultStamp = ResultStampV1` (`stamp.py`), that v1 lives in `stamp_v1.py`, that the shared
  record types live in `stamp_types.py`, and that reading goes through `verify.verify_stamp`. The
  two-stage read (ADR-0006) is spread across the seam rather than sitting behind one interface.
- Proposed change: keep the versioned modules (ADR-0006 forbids editing old ones) but add a single
  `provenance/README`-level entry in `src/provenance/__init__.py` mapping "write → `ResultStamp`",
  "read → `verify_stamp`", "encode → `encoding`", "upstream → `upstream`". No new abstraction.
- Effect: tests that today import from five submodules (`tests/test_one_encoder.py`, `tests/test_stamp_verify.py`)
  keep working; a new contributor finds the seam in one read.
- Strength: Worth exploring · Size: S.

### 1.2 `harness/containment` — 20 modules, one table of assertions
- Files: `harness/containment/__init__.py` (the assertion table), `harness/containment/shells.py` (1341 lines,
  C1/C2/C3/C5/C10/C16/C17), `harness/containment/inside.py` (C8/C9/C12/C13), `harness/containment/reassert.py`
  (C14), `harness/containment/patch_side.py` (C15).
- Problem: the containment seam is split by *which assertions run*, not by *what a caller needs to know*.
  `shells.py` is the one deep module (1341 lines behind a small interface) but `__init__.py` re-exports
  nothing — callers import submodules directly, so the interface is the filesystem. Adding C18 means
  touching the table doc, a new module, and a test file.
- Proposed change: make `harness/containment/__init__.py` the single interface: re-export the assertion
  functions and the `handle` crossing, and keep submodules as implementation. Delete-test signal: deleting
  `__init__.py` today loses nothing, which is the shallow-module smell.
- Effect: containment tests (`tests/...` under `harness/containment/test_*.py`) import from one place;
  new assertions get one registration point.
- Strength: Strong · Size: M.

### 1.3 `scripts/` linters — shared JSON-load + finding logic duplicated
- Files: `scripts/lint_topology.py` (1016 lines), `scripts/lint_invariants.py`, `scripts/lint_adr_numbers.py`,
  `scripts/lint_ci_coverage.py`, `scripts/lint_stage_gates.py`, `scripts/_lintkit.py`.
- Problem: each linter re-implements `_load_json`, finding formatting, and self-test scaffolding. The
  shared `_lintkit.py` exists but the duplication is visible in the imports (each file defines its own
  `REPO_ROOT`/`Findings` usage inconsistently). A new rule author copies a 1000-line file.
- Proposed change: push `_load_json`, `Findings`, and the self-test harness into `_lintkit.py` as the
  single interface; linters become thin rule lists. Deletion test: removing `_lintkit.py` today would
  re-concentrate ~200 lines of boilerplate across five files.
- Effect: new lints are ~30 lines; existing tests (`--self-test` flags) unchanged.
- Strength: Worth exploring · Size: M.

### 1.4 `tools/vaultgraph` — 15 shallow extractors, one pipeline
- Files: `tools/vaultgraph/extract/*.py` (15 files: `code.py`, `documents.py`, `adrs.py`, `decisions.py`,
  `stages.py`, `workflows.py`, `process.py`, `charter.py`, `policy.py`, `references.py`, `imports.py`,
  `layout.py`, `effect.py`, `amendments.py`), `tools/vaultgraph/runner.py`, `tools/vaultgraph/model.py`.
- Problem: each extractor is a module with one or two functions and no shared interface; `runner.py`
  orchestrates by name. Adding a new source type means a new file plus a registration edit in two places.
- Proposed change: define an `Extractor` protocol in `model.py` with `extract(tree) -> list[Node]` and
  move per-source logic behind it. Keep files as adapters at a real seam (two adapters → real seam rule
  satisfied once a second source family exists; today there is only the markdown/code split, so this is
  Speculative).
- Effect: extractor tests in `tools/tests/test_vaultgraph.py` test through the protocol.
- Strength: Speculative · Size: L.

### 1.5 `src/metrics` + `src/domain/trajectory` — already deep (no change)
- `MetricSeries` (`src/metrics/series.py`) and `AgentTrack` (`src/domain/trajectory.py`) carry a large

- `src/mission_control/prototype/` holds a Vercel prototype (`index.html`, `vercel.json`); not referenced

### Change-impact list

  (`StampedResult` digest), `tests/test_measurement_view.py`, `tests/test_provenance.py`.

  `src/replay/harness.py`, `tests/test_s5_ports.py`.
- Change `policy/protected-paths.json` → `harness/patch/validate.py`, `.github/workflows/gates.yml`,
  `docs/tier4/protected-paths-policy.md` (ADR required, D20).
- Change `orchestration/topology.json` → `scripts/lint_topology.py` (TOP001–TOP015), `vault/`, `graph.json`,
  `docs/READING-MAP.md` (regenerate via `tools/gen_vault.py`).
- Change `CLAUDE.md` → must keep `AGENTS.md` byte-identical (twin rule); `docs/README.md` register.

### Is a `map/` shelf worth building here?
No. One `CONTEXT.md` per directory plus the existing vault (`vault/`, `graph.json`) already answers
"what is X" and "what else moves" in two hops. The repo is large but its seams are documented; a `map/`
shelf would duplicate the vault. Recommendation: keep the per-directory `CONTEXT.md` pattern and fix the
two leftovers above instead.
